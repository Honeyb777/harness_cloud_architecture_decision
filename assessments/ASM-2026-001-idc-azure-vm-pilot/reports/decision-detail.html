대상: IDC Java/Kotlin Tomcat 및 Vue 정적 파일 · 검토일: 2026-09-07 · 단계: Discovery

이 보고서는 독립적으로 읽을 수 있는 의사결정 자료입니다. 아래 그림은 현재 권장 흐름이며 아직 확정·구현·검증되지 않았습니다. GitHub repository 권한, Azure RBAC, OIDC federation, Key Vault 접근은 별도 보안·Identity 검토 범위로 제외했습니다.
목표배포 파일을 같은 기준본으로 두 VM에 순차 적용하고, 실패 시 멈추거나 이전 버전으로 되돌릴 수 있게 한다.
현재 확정같은 포트의 Tomcat 교체, Nginx 기반 drain, Actions Cache, Key Vault, 기존 DevOps 도구 비대상.
현재 미확정빌드 이미지, 정식 배포본 저장소, CD 운영, VM 전달, 정적 asset 전환, 운영 수치.

2. 서버 한 대씩 배포하는 흐름

시작 전 확인다른 VM 정상·용량 여유·공통 lock

별도 포트 JVM을 추가하지 않는 현재 방향이다. VM 1의 drain·교체·준비 확인 중 실패하면 상태를 HOLD로 남기고 VM 2 배포를 중단한다. 복구 방식은 이전 WAR/JAR 또는 이전 정적 pointer로 되돌리는 것이다.

3. 선택이 필요한 다섯 가지 정책

빌드 이미지는 어디에 둘 것인가 선택 필요

CI에서는 JDK, Node, 추가 CLI의 버전이 고정된 환경이 필요하다. GitHub-hosted runner 자체와 이 빌드 이미지는 다르다. runner는 작업을 실행하는 VM이고, 빌드 이미지는 workflow가 시작할 때 가져와 사용하는 컨테이너다.

선택설명결정 기준
GHCR private imageGitHub 조직의 private container registry에서 이미지를 가져온다.GitHub 중심 CI이고 Azure runtime container registry가 필요하지 않을 때 적합하다.
ACRAzure Container Registry에서 이미지를 가져온다.Azure private registry 또는 VM runtime container와 registry를 통합해야 할 때 적합하다.
현재 권장: GHCR private image. 현재 VM은 컨테이너를 실행하는 것이 아니라 WAR/JAR과 정적 파일을 배포하므로 ACR 통합의 직접 이점이 확인되지 않았다.

결정 전 확인: 이미지 크기와 pull 시간, 실제 GitHub 계약/사용량, image patch 책임자, 사내 Maven/npm 의존성 공급 경로.

배포 파일의 기준본은 어디에 둘 것인가 선택 필요

배포에 성공한 같은 파일을 VM 1과 VM 2가 사용하고, 필요하면 같은 파일로 rollback해야 한다. 따라서 CI의 임시 cache와 배포 파일 저장소를 구분한다.

선택설명운영 영향
Azure Blob을 기준본으로 사용release ID와 digest를 포함한 immutable 경로에 배포 파일을 둔다.VM이 정해진 파일을 내려받고, 보관·rollback·삭제 보호 정책을 적용하기 좋다.
GitHub Artifacts만 사용CI run에 연결된 artifact를 VM 배포 파일로도 사용한다.run/artifact 수명과 VM 다운로드 방식을 별도로 관리해야 해 rollback 보관이 복잡해진다.
현재 권장: Blob을 정식 배포본으로 사용하고, GitHub Artifacts는 테스트 결과·SBOM·진단 등 CI 증적으로 사용한다.

또는 각 저장소에서 사람이 순서 조정

각 repository의 GitHub concurrency는 그 repository 안의 중복 실행을 막는다. 다른 repository가 같은 VM pair에 동시에 접근하는 문제까지 막지는 못한다.

선택장점감수할 운영 방식
각 저장소에서 수동 조정서비스 팀이 시점과 순서를 직접 통제한다.사람이 공통 lock, 충돌, HOLD 해제를 계속 조정한다.
중앙 deployment repository의 자동 조정대기열, release manifest, 공통 lock과 배포 이력을 한곳에서 관리한다.중앙 repository 운영 책임과 서비스별 release 전달 계약이 필요하다.
현재 권장: 중앙 자동 조정. 공유 VM pair의 동시 drain과 중복 원격 명령 위험을 구조적으로 줄인다.

선택장점확인할 조건
SSH 등 직접 전달흐름이 단순하고 즉시 상태를 보기 쉽다.runner-to-VM 네트워크, SSH credential, host key 및 inbound endpoint가 필요하다.
명령 전달 + VM 파일 내려받기VM의 inbound 배포 endpoint와 파일 전송 credential 요구를 줄일 수 있다.Azure VM Agent, VM egress, Blob 경로, 원격 명령 timeout·취소 상태를 확인해야 한다.
현재 권장: 명령 전달 + VM 파일 내려받기. Azure OIDC는 Azure 제어면 인증이며 SSH 인증을 대신하지 않으므로, VM 직접 접근 요구를 줄이는 장점이 있다.

현재 HTML/assets/r101/app.js
→

해시 또는 release ID 경로를 사용하면 이전 HTML을 가진 브라우저도 r101 파일을 계속 받을 수 있다. 단일 슬롯 교체는 이 파일 요청이 실패할 위험을 수용하는 방식이다.

선택장점운영 영향
단일 슬롯 교체구성과 정리가 단순하다.기존 HTML·browser cache·lazy chunk가 이전 asset을 요청할 때 사용자 영향이 생길 수 있다.
신·구 hash asset 공존VM 순차 전환 중에도 이전 HTML이 필요한 JS/CSS를 받을 수 있다.이전 release와 asset을 정해진 기간 보호하고, cleanup이 이를 삭제하지 않게 해야 한다.
현재 권장: 신·구 hash asset 공존. 실제 frontend build의 asset naming, Nginx 경로, browser cache/service worker 동작은 Pilot에서 확인한 뒤 구현한다.

4. 선택 후 수치와 책임자를 정할 정책

정책정해야 할 내용왜 필요한가
Release lifecycle보관 release 수, rollback 보장 기간, 이전 asset 지원 기간, Cache/Artifact/Image/Blob 보관·삭제·soft delete, 정리 담당자정리 작업이 현재 배포·rollback 파일을 삭제하지 않게 하기 위해서다.
가용성·복구drain 제한 시간, 긴 HTTP 요청/WebSocket 조건, warm-up 관찰 시간, 한 VM 장애 중 허용 용량, HOLD·rollback 기준, RTO/RPO배포 중 장애가 났을 때 다음 VM으로 진행하거나 복구하는 판단 기준이 된다.
패키지·비용사내 Maven/npm 공급원 이관·폐기, image/cache/artifact 처리 시간 측정, retention 비용·예산 경보cache와 artifact가 runner 시간을 줄이는지, 저장 비용을 늘리는지 실제 수치로 판단하기 위해서다.

6. 권장 진행 순서

  1. 중앙 배포 대기열 또는 각 저장소 수동 운영 중 하나를 선택하고, 공통 lock·HOLD 책임자를 정한다.
  2. VM 전달 방식을 선택한 뒤 Blob, VM, runner의 실제 네트워크 경로를 확인한다.
  3. 정식 배포본 저장소와 release lifecycle 값을 정한다.
  4. 빌드 이미지 registry와 정적 asset 전환 방식을 선택하고 실제 build·Nginx 조건을 확인한다.
  5. 개발 환경 Pilot에서 concurrent deploy, drain, warm-up, rollback, release retention, runner 시간을 검증한다.

근거와 참고

이 보고서의 흐름과 선택 기준은 현재 Pilot 요구사항 및 GitHub Actions와 Azure의 공식 기능 문서를 기준으로 정리했다. GitHub는 OIDC, concurrency, cache, artifact 기능을 제공하며 Azure는 Managed Run Command, VM Managed Identity 및 Blob Storage 접근 모델을 제공한다. 실제 기능 사용 가능 여부와 과금은 조직 계약·리전·환경 설정에서 재확인해야 한다.

  • GitHub Actions: Azure OIDC 구성
  • GitHub Actions: concurrency 제어
  • Azure VM: Run Command
  • Azure Blob: Managed Identity 기반 데이터 접근
